Instead of dumping everything into one giant prompt, they built a set of
specialized agents that work together. one clever move is using dynamic fewshot learning — they search a vector db for similar examples, then combine
those with a pruned schema and the user’s intent before sending it to the
model. it’s leaner, faster, and smarter.
In this post, we’ll build a similar setup using neo4j for vector storage and
show how each agent works. the code is inspired by querygpt’s ideas, but
with my own edits to fit real-world use.
At the end, i’ll also share how i optimized this pipeline for a client project
and what made the biggest impact.
The Multi-Agent Philosophy
The beauty of QueryGPT’s architecture lies in its recognition that different
aspects of sql generation require different types of reasoning. rather than
 
using a single large language model to handle everything, the system
employs specialized agents that work together in a coordinated pipeline.
Each agent has a specific role and can be optimized independently, allowing
for better performance and resource utilization.
It vectorized user prompts and performed similarity searches on sql samples
and schemas to identify pertinent tables and query examples , but the real
breakthrough came when they realized that different agents could use
different models based on their specific requirements.
1. intent agent — narrowing the search space
prompt = f"""
Based on the following user query, determine which workspace or workspac
The available workspaces are: {', '.join(self.workspaces)}
User Query: "{user_query}"
Respond with a JSON object with the following structure:
{{
"workspaces": ["workspace1", "workspace2"], // List of relevant work
"explanation": "Brief explanation of why these workspaces were chose
}}
"""
The first step in the pipeline is the intent agent. Its job is to look at the user’s
natural language question and figure out what business domain or
workspace it maps to. eg : is the user asking about payments, customer
behavior, or product inventory ?
Once the intent is inferred, it helps us do two things:
 
limit which tables are even considered in the next step
retrieve more relevant few-shot examples from a vector database
This drastically reduces the noise. instead of searching across the entire
schema and all samples, we now work within a smaller, domain-specific
context.
In our setup we run a lightweight model (like gpt-4o-mini) for this task. it’s
fast, doesn’t need deep reasoning, and just needs to make a decent
classification based on the user prompt.
2.table agent — validating table selection
prompt = f"""
Based on the following user query and database schema, determine which t
User Query: "{user_query}"
Workspace: {workspace}
Database Schema:
{schema_text}
Respond with a JSON object with the following structure:
{{
"tables": ["table1", "table2"], // List of required tables
"explanation": "Brief explanation of why these tables were chosen"
}}
"""
Next we have the table agent. the uber team found that sometimes
QueryGPT would pick the wrong tables for a query. to fix this they added the
Table Agent. this agent’s role is to look at the user’s question and the
 
identified intent and then propose a list of the most likely tables needed to
answer the query.
This list of tables is then shown to the user who can either give a thumbs up
or make changes. this human-in-the-loop approach is a great way to improve
accuracy and build trust in the system. it ensures that the final query is built
on the correct foundation.
3. column prune agent — shrinking the schema
prompt = f"""
Based on the following user query and the tables that have been selected
User Query: "{user_query}"

{schema_text}
For each table, return only the columns that are necessary to answer the
Respond with a JSON object with the following structure:
{{
"pruned_schema": {{
"table_name1": ["column1", "column2"],
"table_name2": ["column1", "column3"]
}},
"explanation": "Brief explanation of why these columns were chosen"
}}
"""
Once we’ve picked the right tables, we still face a challenge: some tables
have dozens (or hundreds) of columns, and we don’t need all of them in
every prompt. in fact feeding all those columns into the llm causes prompt
bloat, token overuse, and even model failure on long requests.
This is where the column prune agent comes in. it acts as a filter, deciding
which columns actually matter for the current query. we use an llm to do
this because the context of the question matters. eg : if a user asks “show me
customers who spent more than $1000,
” we don’t need the birth_date or
email columns—just the ones related to spending.
This step had a surprising impact. it not only reduced token usage (and
therefore cost), but it also sped up inference and improved sql quality.
After experimenting with different models, i found that this step benefits a
lot from a stronger model. pruning irrelevant columns while keeping query
fidelity requires deeper reasoning, so using GPT-4.1, Gemini 2.5 Pro, or
Claude Opus 4 worked significantly better than smaller models.
4.few-shot search — learning from examples
Now that we’ve figured out the intent and pruned the schema, we can finally
retrieve relevant few-shot examples. these are embedded queries paired with
natural language that are stored in a vector database. when a new query
comes in, we search for similar examples based on the intent and use them
as demonstrations.
Instead of using static prompts, this makes the system adaptive. it’s closer to
how humans would work — looking at previous examples of similar tasks
before starting from scratch.
For this part, we created our own embeddings, pushed them into a neo4jbased vector store, and built a simple retrieval system to fetch them based
on cosine similarity. you’ll see how in the next section when we walk
through the code.

Finally, with the pruned schema and curated examples, we ask the llm to
generate the actual sql query. at this point it has all the context it needs: a
slimmed-down schema, relevant tables, examples that match the intent, and
even system instructions or hints if needed.
This step can run on a reasonably powerful model , if everything else is well
prepared, the query generation itself is fairly straightforward.

Creating a test database schema
This function builds a rich, relational sqlite database representing a
university system with departments, students, professors, courses,

def create_db(db_name="sample_retail.db"):
conn = None
try:
conn = sqlite3.connect(db_name)
cursor = conn.cursor()
# Enable foreign keys
cursor.execute("PRAGMA foreign_keys = ON")
# Drop tables if they exist (to reset) - Drop in reverse order of creati
tables = [
"attendance", "grades", "enrollments", "course_professors",
"schedules", "classrooms", "courses", "students", "professors",
"departments"
]
for t in tables:
cursor.execute(f"DROP TABLE IF EXISTS {t}")
# Departments
cursor.execute("""
CREATE TABLE departments (
id INTEGER PRIMARY KEY,
name TEXT NOT NULL,
building TEXT
)
""")
# Professors
cursor.execute("""
CREATE TABLE professors (
id INTEGER PRIMARY KEY,
name TEXT NOT NULL,
email TEXT UNIQUE,
department_id INTEGER,
FOREIGN KEY(department_id) REFERENCES departments(id)
)
""")
# Students
cursor.execute("""
CREATE TABLE students (
id INTEGER PRIMARY KEY,
name TEXT NOT NULL,
email TEXT UNIQUE,
dob DATE,
department_id INTEGER,
FOREIGN KEY(department_id) REFERENCES departments(id)
)
""")
# Courses
cursor.execute("""
CREATE TABLE courses (
id INTEGER PRIMARY KEY,
title TEXT NOT NULL,
code TEXT UNIQUE,
credits INTEGER,
department_id INTEGER,
FOREIGN KEY(department_id) REFERENCES departments(id)
)
""")
# Classrooms
cursor.execute("""
CREATE TABLE classrooms (
id INTEGER PRIMARY KEY,
building TEXT,
room_number TEXT,
capacity INTEGER
)
""")
# Schedules (when and where a course happens)
cursor.execute("""
CREATE TABLE schedules (
id INTEGER PRIMARY KEY,
course_id INTEGER,
classroom_id INTEGER,
day_of_week TEXT,
start_time TEXT,
end_time TEXT,
FOREIGN KEY(course_id) REFERENCES courses(id),
FOREIGN KEY(classroom_id) REFERENCES classrooms(id)
)
""")
# Course Professors (many-to-many)
cursor.execute("""
CREATE TABLE course_professors (
id INTEGER PRIMARY KEY,
course_id INTEGER,
professor_id INTEGER,
FOREIGN KEY(course_id) REFERENCES courses(id),
FOREIGN KEY(professor_id) REFERENCES professors(id)
)
""")
# Student Enrollments (many-to-many)
cursor.execute("""
CREATE TABLE enrollments (
id INTEGER PRIMARY KEY,
student_id INTEGER,
course_id INTEGER,
enrollment_date DATE,
FOREIGN KEY(student_id) REFERENCES students(id),
FOREIGN KEY(course_id) REFERENCES courses(id)
)
""")
# Grades (1-to-1 with enrollment)
cursor.execute("""
CREATE TABLE grades (
id INTEGER PRIMARY KEY,
enrollment_id INTEGER,
grade TEXT,
FOREIGN KEY(enrollment_id) REFERENCES enrollments(id)
)
""")
# Attendance (multi-dimensional relation)
cursor.execute("""
CREATE TABLE attendance (
id INTEGER PRIMARY KEY,
enrollment_id INTEGER,
date DATE,
present BOOLEAN,
FOREIGN KEY(enrollment_id) REFERENCES enrollments(id)
)
""")
conn.commit()
print(f"Database '{db_name}' created .")
except sqlite3.Error as e:
print(f"Database error: {e}")
finally:
if conn:
conn.close()
# Run the script
if __name__ == "__main__":
create_db()

Extracting structured database schema metadata
def get_database_schema():
"""Extract schema information from the database"""
conn = sqlite3.connect('sample_retail.db')
cursor = conn.cursor()
# Get list of tables
cursor.execute("SELECT name FROM sqlite_master WHERE type='table'")
tables = cursor.fetchall()
schema_info = {}
for table in tables:
table_name = table[0]
cursor.execute(f"PRAGMA table_info({table_name})")
columns = cursor.fetchall()
# Format column information
column_info = []
for col in columns:
column_info.append({
'name': col[1],
'type': col[2],
'primary_key': bool(col[5]),
})
schema_info[table_name] = {
'columns': column_info,
'description': f"Table containing {table_name} information"
}
conn.close()
return schema_info

IntentAgent — mapping queries to relevant domains
The IntentAgent identifies which business domain(s)—or workspaces—a
user's query belongs to. this is the first step in the QueryGPT-style pipeline. it
uses a system prompt to guide an llms in selecting from a predefined list of
workspace categories (eg student management, attendance tracking, etc.)

QueryGPT — the orchestrator of the full NL-to-SQL pipeline
The QueryGPT class brings everything together. it runs a complete pipeline
that converts a user's natural language question into sql by coordinating all
the sub-agents:
1. Intent detection — narrows down the domain to filter the search space.
2. Table selection — identifies only the tables relevant to the user’s intent.
3. Column pruning — reduces token bloat by keeping only essential
columns.
4. Few-shot retrieval — pulls similar embedded examples to guide the llm
5. SQL generation — builds the final query with explanation using a wellcrafted prompt.
6. Query execution — runs the query to validate and show actual results.

Architecture Benefits
The multi-agent approach delivers several key advantages over monolithic
systems.
first, it’s more maintainable — each agent can be developed, tested, and
optimized independently.
second, it’s more cost-effective — you can use the right model for each task
rather than over-provisioning everywhere.
third, it’s more transparent — users can see and influence the decisionmaking process at each stage.
Perhaps most importantly, this architecture is more resilient. if one agent
makes a mistake, the others can often compensate, and the modular design
makes it easier to identify and fix issues when they arise.
WhatYouCan Optimize (WhatI Did in My UseCase)
This setup is just a starting point — enough to show how the querygpt
architecture works, but there’s plenty of room to tweak it based on your data
and needs.
Here are a few key optimizations i made in my own use case:
Model selection by task: small models (like GPT-4o-mini or GPT-4.1-mini)
work well for intent classification or table selection, but schema pruning and
sql generation benefit from larger models like GPT-4.1, Claude 4 Opus, or
Gemini 2.5 Pro. in my case, i used task-specific models for better costperformance trade-offs.
Use metadata filtering in RAG: i embedded the workspace tags with each
query and used them as metadata filters. this narrowed down the candidate
set during retrieval and made it more accurate and efficient.
Tune the retrieval k : play around with how many similar examples ( k ) you
retrieve. more isn't always better—larger k eats up context and can distract
the model. match k to your model’s context window and your prompt
design.
Improve in-context learning: add more diverse, well-labeled few-shot
examples across different scenarios. this helps the sql generator generalize
better across edge cases and domain shifts.
Customize the SQL prompt: this is one of the most important levers. i iterated
on the SQLGenerator prompt to make it reflect real-world constraints (e.g.,
no SELECT *
, handle ambiguous joins, qualify columns) and updated it as i
discovered failure modes.
Keep a human in the loop: don’t expect perfect answers on the first try. let
users inspect intermediate outputs (intent, tables, schema), adjust them, and
rerun. this interactive loop is often more reliable than a fully automatic
system.
Evaluate numerically: i logged structured outputs and manually reviewed
them to build evaluation sets. don’t just trust qualitative output — track
success rates, schema accuracy, and sql execution results.
Add observability: i integrated Langfuse to monitor the pipeline end-to-end.
it helped me collect structured traces, analyze feedback (positive/negative),
and iterate quickly post-deployment. that observability was crucial after
releasing the beta.
Start with closed-source LLMs, then fine-tune smaller open models: use
high-quality models like GPT-4.1 or Claude 4 Opus in the beta phase to
collect structured usage data and user feedback. once you have enough
examples, you can fine-tune smaller open-source models (like Qwen3-4B128K ) for specific agents like sql generation or column pruning —
dramatically cutting costs while maintaining performance..
Add fixed few-shot examples to prompts (for classification agents): i found
that hard-coding a few high-quality examples directly in the prompts —
especially for IntentAgent , TableAgent , and ColumnPruneAgent —can
significantly improve consistency. it gives the model clearer grounding,
especially when incoming queries are noisy or ambiguous.
Add explanation field : adding an explanation field to each agent’s output
schema helps you understand why the llm made a certain decision. this
makes it easier to debug, tune prompts, provide more context, or even swap
in a different model if needed. it's a simple addition that gives you much
better visibility into model behavior.
QueryGPT’s setup is a great example of how breaking things into smaller
parts can make NL2SQL systems smarter and easier to manage. instead of
one big model doing everything, it uses a bunch of focused agents — each
handling a specific task like intent detection, table selection, or schema
pruning. this makes the system faster, cheaper, and easier to debug. and
because it’s modular, you can easily swap models, add feedback, or fine-tune
parts of it as you go. with a bit of tuning and the right observability tools, it’s
a solid base for building smart and flexible data agents.
